# Диплинк-трансляция оператора — индекс задач (backend)

> Проект: `seating-generator-backend` (Kotlin / Ktor / Exposed ORM / Protobuf / MySQL) · Статус набора: на ревью

Набор backend-задач под фичу **«Запуск трансляции оператором по диплинку (`mafbase_stream`)»**: организатор турнира/клуба раздаёт камер-операторам простые ссылки вида `…/broadcast?tournamentId|clubId=…&table=…&key=…`, по которым оператор без логина получает RTMP-креды конкретного стола и одной кнопкой запускает стрим. Полный контекст, флоу и требования — в [BRD](../../brd-operator-broadcast-deeplink.md). Бэкенд закрывает блокеры из BRD §7: эндпоинт выдачи RTMP-кредов по `key` без auth (FR-6), клубные RTMP-эндпоинты и хранение по столам (FR-10, FR-11), хостинг `apple-app-site-association` для iOS universal links (FR-5).

Каждый файл задачи — самодостаточная спецификация для отдельного ревью и реализации (как правило отдельным агентом и отдельным коммитом в `seating-generator-backend`).

## Зафиксированные решения

Принятые пользователем решения (закрывают «открытые вопросы» BRD §7). Обязательны для всех задач.

| # | Решение | Следствие |
|---|---|---|
| **D1** | Токен диплинка оператора = **отдельный per-table broadcast-токен** (SecureRandom, хранится в БД по каждому столу, ротируемый). НЕ переиспользуем translation-key `hash(id+salt)`. | Новая колонка `broadcast_token` (миграции V3/V5), генерация SecureRandom при `setStream`, отдельный эндпоинт ротации. Право публикации отделено от translation-key (закрывает открытый вопрос BRD §7.1). |
| **D2** | Жизненный цикл ссылки = **бессрочный до ротации токена**. Без TTL, без одноразовости. | Эндпоинт кредов не проверяет срок/счётчик; инвалидация ссылок происходит только через ротацию (механизм NFR-1). Закрывает открытый вопрос BRD §7.2. |
| **D3** | Клубные стримы **переиспользуют** существующие proto-сообщения `GameStream` / `GameStreamAdmin` / `SetStreamEvent` / `GetStreamsOut` / `GetStreamsAdminOut` (они не содержат `tournamentId` — сущность задаётся роутом). Новые клубные stream-сообщения **не заводим**. | Задача 03 не добавляет proto-сообщений для клубных стримов; различает турнир/клуб через путь. Корректирует FR-11 (новые сообщения не нужны). |
| **D4** | Блокировка параллельных операторов на одном столе — **вне scope бэкенда** (ответственность RTMP-сервера). | Бэкенд не сериализует publish; зафиксировано как ограничение. Закрывает открытый вопрос BRD §7.3. |
| **D5** | Overlay-константа `plashkiMafbase` задаётся **на клиенте**; бэкенд только хранит/отдаёт `breakPlaceholderImageUrl` + `brandImageUrl` (+ опц. `overlayDesignKey`). | Задача 02 хранит только URL-поля overlay (миграция V4) и отдаёт их в `BroadcastCredentialsOut`; сам дизайн-набор плашек на бэке не моделируется. |

## Граф зависимостей и критический путь

```
                 ┌─────────────┐
                 │ 00  proto   │
                 └──────┬──────┘
          ┌────────────┼────────────┐
          ▼            ▼            ▼
   ┌──────────┐  ┌──────────┐  ┌──────────┐      ┌──────────┐
   │ 01 креды │  │ 02 over- │  │ 03 club  │      │ 04 AASA  │
   │  (тур.)  │  │   lay    │  │  streams │      │ (незав.) │
   └────┬─────┘  └────┬─────┘  └────┬─────┘      └────┬─────┘
        │  02 обогащает│ ответ 01    │ 03 расширяет     │
        │  overlay-полями (до этого  │ эндпоинт 01      │
        │  они null)   │             │ клубной веткой   │
        └─────────────┴─────────────┴──────────────────┘
                              ▼
                      ┌──────────────┐
                      │ 05 тесты/    │
                      │  верификация │
                      └──────────────┘
```

- **00 → (01, 02, 03)**: все три задачи потребляют proto-сообщения из 00 (`BroadcastCredentialsOut`, `broadcastToken` в `GameStreamAdmin`, `SetStreamSettingsEvent` / `StreamSettingsOut`). 00 — единственный владелец proto-изменений; остальные задачи только потребляют.
- **02 обогащает 01**: до выполнения 02 эндпоинт кредов отдаёт `breakPlaceholderImageUrl` / `brandImageUrl` как `null`; 02 наполняет эти поля из хранилища overlay-конфига (миграция V4).
- **03 расширяет 01**: добавляет клубную ветку (`clubId` вместо `tournamentId`) в тот же эндпоинт `GET /api/broadcast/credentials`, переиспользуя паттерн доступа по `key` → 403/404.
- **04 независима** от 00–03 (хостинг статических файлов / роутов AASA).
- **05 после всех** — интеграционная верификация и тесты.
- **Критический путь для разблокировки клиента**: **00 → 01** (турнирный флоу оператора). Этого достаточно, чтобы клиент начал реализацию резолвера `/broadcast` для турниров; клубный флоу (03) и overlay (02) подключаются итеративно.

## Вне scope (всей итерации)

- **D4** — блокировка параллельных операторов на одном столе (ответственность RTMP-сервера, не бэкенда).
- Зрительский экран просмотра трансляции в приложении.
- Авторизация / роли операторов (осознанно отказались — доступ только по `key`).
- Генерация диплинков на бэке — ссылки строятся на клиенте из параметров (`tournamentId|clubId + table + key`).
- VK-генерация (`StartVkStreamEvent` / `video.startStreaming`) для клубов — клубные стримы только ручной ввод RTMP.

## Порядок ревью / апрува

- Каждый файл задачи (00–05) — **self-contained**: содержит свой контекст, объём, точные технические детали (proto / SQL / сигнатуры) и проверяемый Definition of Done. Ревьюится и принимается **независимо**.
- Рекомендуемый порядок апрува = порядку графа: сначала **00** (фиксирует контракт proto и номера полей), затем параллельно **01 / 02 / 03**, независимо **04**, в конце **05**.
- При расхождении любой задачи с этим индексом или с зафиксированным контрактом — приоритет у контракта; задачу отклонить и привести в соответствие.
- Реализация — отдельный коммит в `seating-generator-backend` на задачу (proto-изменения 00 — также коммит/пуш сабмодуля `seating-generator-proto`). Git-операции выполняются только внутри проекта, не из корня workspace.
