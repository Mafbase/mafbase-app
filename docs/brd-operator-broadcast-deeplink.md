# BRD — Запуск трансляции оператором по диплинку (mafbase_stream)

> Статус: черновик · Дата: 2026-06-19 · Ветка: `feat/mafbase-stream`

## 1. Цель и контекст

Дать организатору турнира/клуба возможность **раздать камер-операторам простые ссылки**, по которым человек с установленным приложением Mafbase сразу попадает на экран трансляции конкретного стола и запускает RTMP-стрим **одной кнопкой** — без логина, без ручного ввода ключей и серверов.

Сегодня:
- Нативный экран трансляции (`MafbaseStream.openStreamScreen`) **уже реализован** (iOS/Android), но **не вызывается из приложения**.
- Турнир уже умеет хранить RTMP server/key **по столам** (`StreamsPage` + `StreamRepository.setStream`).
- Клуб **не умеет** вводить RTMP server/key (только ключ для зрителей).
- iOS-диплинки **не работают** (нет Associated Domains / AASA).

## 2. Глоссарий

| Термин | Значение |
|---|---|
| **Организатор** | Админ турнира или владелец клуба, настраивает трансляцию и раздаёт ссылки |
| **Оператор** | Человек с телефоном и приложением, физически снимает стол и жмёт «Начать» |
| **Диплинк оператора** | Ссылка на конкретный стол: `…/broadcast?tournamentId|clubId=…&table=…&key=…` |
| **`key`** | Токен доступа в URL. По нему бэкенд отдаёт RTMP-креды; сам RTMP-ключ в URL не передаётся |
| **Нативный экран** | `StreamViewController` (iOS) / `StreamActivity` (Android) — превью камеры + кнопка старт/стоп |

## 3. Акторы и роли

1. **Организатор турнира** (есть права админа турнира) — вводит RTMP server/key по столам, копирует диплинки операторов.
2. **Организатор клуба** (владелец клуба) — то же, в клубной админке (**новое**).
3. **Оператор** — открывает диплинк, **без аккаунта/логина**, попадает в нативный экран, жмёт «Начать трансляцию».

## 4. Пользовательские флоу

### 4.1 Турнир (организатор)
1. Открывает `StreamsPage` турнира → для каждого стола вводит/проверяет RTMP server + key (как сейчас).
2. Рядом со столом — новая кнопка **«Ссылка оператора»** → копирует диплинк стола.
3. Отдаёт ссылку оператору (мессенджер/QR/распечатка).

### 4.2 Клуб (организатор) — **новое**
1. Открывает новую клубную админку трансляций → вводит RTMP server + key по столам (зеркало турнира).
2. Копирует диплинк оператора для каждого стола.

### 4.3 Оператор (турнир и клуб одинаково)
1. Открывает диплинк → приложение (по universal/app-link) запускается.
2. Приложение по `key` запрашивает у бэка RTMP server/key + overlay-конфиг стола (без логина).
3. **Сразу** открывается нативный экран `mafbase_stream` (превью камеры).
4. ОС запрашивает доступ к камере/микрофону (первый раз).
5. Оператор жмёт **одну кнопку** → стрим пошёл. Повторное нажатие — стоп.

## 5. Функциональные требования

**Диплинк и роутинг**
- **FR-1.** Новый маршрут `BroadcastRoute` (например `/broadcast`) с query-параметрами `tournamentId`, `clubId`, `table`, `key` (по образцу существующего `/translationControl`).
- **FR-2.** Маршрут — **резолвер**: парсит параметры → запрашивает креды с бэка → немедленно вызывает `openStreamScreen(...)`. Видимого Flutter-UI нет, кроме индикатора загрузки и экрана ошибки (невалидный/протухший `key`, нет сети, стол не настроен).
- **FR-3.** Маршрут доступен **без авторизации** (вне `AuthGuard`).
- **FR-4.** Android: добавить путь `/broadcast` в `intent-filter` (`https://mafbase.ru/broadcast`).
- **FR-5.** iOS: настроить Associated Domains + хостинг `apple-app-site-association` на `mafbase.ru` (бэкенд-зависимость). Опционально — кастомная схема `mafbase://broadcast` как фолбэк.

**Получение кредов**
- **FR-6.** Бэкенд-эндпоинт «отдать RTMP-креды стола по `key`» (без auth): вход `tournamentId|clubId + table + key` → выход `rtmpServerUrl`, `rtmpKey`, overlay-конфиг (`overlay`, `breakPlaceholderImageUrl`, `brandImageUrl`). Невалидный `key` → 403.
- **FR-7.** Приложение мапит ответ в `openStreamScreen`: `rtmpUrl`+`streamKey` из кредов; `tournamentId`/`clubId`+`table` из URL; overlay = `plashkiMafbase`; `breakPlaceholderImageUrl`/`brandImageUrl` из конфига.

**Админка — турнир**
- **FR-8.** В `StreamsPage` для каждого стола — действие **«Ссылка оператора»** (копировать + показать QR). Ссылка строится из `tournamentId + table + key`.

**Админка — клуб (новое, зеркало турнира)**
- **FR-9.** Новая страница управления RTMP-трансляциями клуба: список столов, ввод `rtmpServerUrl`/`rtmpKey`/`viewerUrl` по столу (по образцу `AddStreamBottomSheet`).
- **FR-10.** Клубный репозиторий + методы `setStream/getStreamsAdmin` по `clubId` (зеркало `StreamRepository`).
- **FR-11.** Новые proto-сообщения для клубных стримов (зеркало `GameStreamAdmin`/`SetStreamEvent`, но на `clubId`).
- **FR-12.** Кнопка **«Ссылка оператора»** по столу в клубной админке.

**Нативный экран**
- **FR-13.** Запуск/остановка стрима одной кнопкой — уже реализовано, переиспользуем как есть. Закрытие экрана возвращает в приложение (или закрывает, если открыто холодным стартом по ссылке).

## 6. Нефункциональные требования

- **NFR-1 (Безопасность).** RTMP-ключ **не передаётся в URL** — только токен `key`. Раскрытие диплинка = возможность публиковать на конкретный стол; радиус поражения ограничен одним столом. Митигация: ротация `key` инвалидирует старые ссылки; rate-limit на эндпоинт кредов.
- **NFR-2 (Платформы).** iOS + Android. Камера/микрофон — обязательны; обработать отказ в разрешениях.
- **NFR-3 (Холодный старт).** Диплинк должен открывать экран при полностью закрытом приложении (не только из foreground).
- **NFR-4 (Локализация).** Все новые строки — в `app_ru.arb`.
- **NFR-5 (UX ошибок).** Понятные сообщения: «Ссылка устарела», «Стол не настроен для трансляции», «Нет доступа к камере».

## 7. Зависимости и риски

**Бэкенд (блокеры):**
- Эндпоинт выдачи RTMP-кредов по `key` без auth (FR-6).
- Клубные RTMP-эндпоинты + хранение по столам (FR-10).
- Хостинг `apple-app-site-association` для iOS universal links (FR-5).

**Proto:**
- Новые сообщения для клубных стримов (FR-11). ⚠️ Уже всплыл конфликт сабмодуля `seating-generator-proto` при ребейзе — этот repo придётся мержить, и клубные стрим-сообщения логично добавить там же.

**Открытые вопросы:**
1. **Что такое `key`** — переиспользуем существующий translation-key (тот, что уже в `/translationControl`) или заводим **отдельный broadcast-токен**? Переиспользование проще, но один ключ начинает давать и контроль контента, и право публикации. Рекомендуется отдельный токен.
2. **Жизненный цикл ссылки** — бессрочная до ротации ключа, или с TTL/одноразовая?
3. **Параллельные операторы** — что если двое откроют ссылку одного стола одновременно? Бэк разрешает/блокирует второй publish?
4. **Закрытие экрана** при холодном старте по ссылке — куда возвращать (на `/club`? закрыть приложение?).

## 8. Вне scope (этой итерации)
- Зрительский экран просмотра трансляции в приложении.
- Авторизация/роли операторов (осознанно отказались).
- Генерация ссылок на бэке (строим на клиенте из параметров).

## 9. Предлагаемые этапы реализации
1. **Proto + бэкенд-контракты** (клубные стримы, эндпоинт кредов по `key`) — согласовать раньше всего, блокеры.
2. **Резолвер-маршрут `/broadcast`** + интеграция `openStreamScreen` (турнир-флоу).
3. **Платформенная конфигурация диплинков** (Android intent-filter, iOS AASA + entitlement).
4. **Кнопка «Ссылка оператора»** в турнирной `StreamsPage`.
5. **Клубная RTMP-админка** (страница, репозиторий, proto) + кнопка ссылки.
6. **Локализация, обработка ошибок, golden-тесты** новых страниц.
